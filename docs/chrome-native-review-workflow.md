# 通过 Chrome 原生界面提交审核

确认日期：2026-11-12（北京时间）。龙海要求以后发布按本流程操作。适用于 oh-my-x 的 Chrome 商店更新；版本号、线上版本和字段内容每次重新核实。

## 采用的方式

使用 `mcp__cua_repl.js` 控制 Mac 上的 Google Chrome 原生窗口，读取无障碍树（系统提供的界面结构）并操作后台表单。优先复用用户已登录的开发者后台。

事实：3.0.0 于 2026-11-12 14:10 提交成功，后台显示「已将您的扩展程序提交送审」和「待审核」，保留审核通过后自动发布。提交前已发布版本为 2.9.0。完整记录见 [3.0.0 送审说明](releases/v3.0.0-store.md)。

事实：同日浏览器扩展控制工具导航到商店后台返回 `Not allowed`，原生界面操作成功。拒绝的具体原因未知，不能据此判断账号或安装包有问题。商店接口脚本当时缺少授权凭据，不作为默认流程；本次没有使用远程调试。

## 1. 准备版本和材料

1. 核对发布范围，更新版本号、锁文件及中英文更新记录。运行与改动匹配的验证；从目标发布提交的干净目录打包。
2. 上传商店的文件为 `build/oh-my-x-<版本号>-chrome.zip`，由 `npm run zip` 生成。检查 ZIP 根目录有 `manifest.json`，版本号与目标一致，并记录 SHA-256（文件校验值）。
3. GitHub 的 `oh-my-x-chrome-mv3.zip` 顶层有 `chrome-mv3/` 文件夹，是手动安装包，不用于商店上传。
4. 准备中英文完整介绍、累计更新、权限用途、数据使用说明和隐私政策地址。以后台实际已发布版本为比较基线；例如本次是 2.9.0 → 3.0.0，包含未上架的 2.10.0 改动。
5. 可将材料及商店包复制到 `~/Downloads/oh-my-x-<版本号>-chrome-submission/`，方便系统文件选择器定位。文件名必须换成本次版本。

GitHub 发布和 Chrome 送审分别记录。运行 `gh` 命令时显式指定 `-R longhaiqwe/oh-my-x`，避免默认选到上游仓库。

## 2. 接入已登录的 Chrome

先按当前工具要求读取操作说明。首次 CUA（电脑界面操作工具）调用只绑定应用：

```javascript
let chromeNative = await cua.getApp('/Applications/Google Chrome.app');
```

本次按应用标识选择时出现同名路径歧义，使用完整路径成功。已有可用绑定时继续复用。上下文压缩后先调用 `await cua.rewriteDocumentation()` 恢复说明，再操作。

- 用户已经登录就直接继续；需要登录时由用户完成。
- 确认商品为 `oh-my-x`，商品 ID 为 `ehnedndgpdkclhddhgdkdadhbiafaend`。
- 在[软件包页](https://chrome.google.com/webstore/devconsole/fb54ced2-ce3b-4996-93ec-18575bd9588c/ehnedndgpdkclhddhgdkdadhbiafaend/edit/package)读取「已发布」和「草稿」版本，并检查是否已有在审版本。
- 每轮操作后调用 `getAXState()` 读取新状态，再决定下一步。元素编号会变化，不能沿用历史会话中的编号。
- 状态太长时，用 `{emit:false}` 接收后只输出相关段落。需要截图时单独调用 `getScreenshot()`；截图后若继续按编号操作，先重新读取完整树。

## 3. 上传商店包

1. 点击「上传新的软件包」→「选择文件」。
2. 系统文件窗口出现后，按 `super+shift+g` 打开「前往文件夹」，读取新状态。
3. 对当前 `PathTextField` 设置本次 ZIP 的完整绝对路径。先确认界面显示完整路径，再确认。
4. 用 `KP_Enter` 确认路径，读取新状态。核对选中的 ZIP 文件名，再点击「打开」。
5. 等待「正在上传」和「正在处理」结束。上传后可能自动跳到商品详情；回到「文件包」，确认草稿版本为本次版本。

文件窗口排查：本次普通 `Return`、粘贴和双击曾未达到预期。重新取得当前应用窗口、对暴露了 `Raise` 动作的窗口执行该动作、用 `setValue` 设置路径，再用 `KP_Enter` 后成功。下列变量必须来自当前界面，不能猜编号：

```javascript
// 仅在当前窗口实际暴露 Raise 时使用。
await chromeNative.performSecondaryAction(windowIndex, 'Raise');
await chromeNative.setValue(pathFieldIndex, absoluteZipPath);
await chromeNative.getAXState();
// 确认界面中的完整路径正确后：
await chromeNative.pressKey('KP_Enter');
await chromeNative.getAXState();
```

输入未生效时先检查焦点、当前窗口和截图，不连续重复同一失败动作。仍无法完成才请用户协助选文件；之后继续其余流程。

## 4. 更新商品与隐私资料

1. 「商品详情」分别切换英语与简体中文，填写完整介绍及累计更新。每种语言点击「保存草稿」，确认「已成功保存内容」后再切换。保留仍适用的截图、分类和链接。
2. 「隐私权」核对单一用途、各项权限、主机权限和数据使用。即使没有新增权限，功能用途变化也要同步说明。
3. 本次权限理由字段上限为 1000 字符，主机说明实际保存 926 字符；介绍字段上限为 16000 字符。以后以当次界面上限为准，不能直接粘贴超长材料。
4. 数据类型按当次代码行为和后台定义填写。3.0.0 勾选个人身份信息、身份验证信息、网络记录、用户活动、网站内容；这是该版本记录，不是以后固定照抄的选项。
5. 本次隐私政策字段沿用 `https://raw.githubusercontent.com/longhaiqwe/oh-my-x/main/PRIVACY.md`。原有 GitHub 页面链接曾校验超时，已验证有效的地址不要无故替换。
6. 保存并确认成功，处理界面显示的实际错误。既有三项用途声明本次保持勾选；如后续出现新的协议或授权要求，按当时工具规则处理。

本次隐私页未显示单独的「远程代码」字段。旧资料有该字段，不要因当前界面没有而推测漏填。

## 5. 提交并核实结果

1. 在商品详情点击「提请审核」。
2. 确认框中沿用「通过审核后自动发布」；用户另有要求时按当次要求设置。
3. 用户已明确要求提交审核时继续点击「提交审核」，无需再重复询问同一项授权。
4. 等待提交完成，以「已将您的扩展程序提交送审」或后台明确的待审核状态为完成证据。点击过按钮、上传成功或草稿版本正确，都不能单独算送审成功。
5. 保存显示成功提示和商品背景的截图，交付时直接展示。截图留在本机材料文件夹，避免将包含其他标签页的完整截图提交到公开仓库。
6. 观察到最终结果后，下一次工具调用按 CUA 要求仅发送 `completion_summary`，结束界面操作。
