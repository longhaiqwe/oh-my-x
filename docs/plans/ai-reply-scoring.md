## 1. 目标

在现有「评论垃圾过滤」上加一层模型打分。

- 每条回复得到一个 AI 嫌疑分（0–100），附命中的信号编号和一句理由。
- 分数 ≥ 阈值的回复折叠成一行，可以展开，不删除。
- 默认只在**自己帖子**的详情页自动判断；别人的帖子手动点按钮判断。
- 用户可以把一条回复标成「机器人」或「真人」，标注存在本地，可以导出。
- 规则过滤照旧，模型只处理规则没隐藏的回复。

这次不做：

| 不做 | 原因 |
|---|---|
| 三项分数（AI 概率 / 低信息量 / 引流） | 引流已有规则（`mention_referral`、垃圾词库）；低信息量和「万能回复」「复述原帖」两个信号重叠 |
| 拦截接口取作者的注册时间、简介 | 粉丝数和蓝 V 用页面上已有的数据，提示词第 2 版已经送（4.1）；注册时间、简介等以后用样例集做对比实验再定 |
| 模拟点击 X 菜单拉黑、静音 | 有被 X 限制的风险，另议 |
| 结果出来前先隐藏 | 自动判断只在自己帖子下进行，等待 2 秒左右，先显示 |
| 对主帖打分 | 范围外 |

## 3. 整体流程

```
扫描到一条回复
  ├─ 黑名单 → 隐藏（现有）
  ├─ 白名单 / 自己的回复 / 主帖作者的回复 / 已标「真人」 → 放行
  ├─ 规则分 ≥ 阈值 → 隐藏（现有）
  └─ 其余 → 取推文 ID
        ├─ 本页内存里有结果 → 直接用
        ├─ 后台缓存里有结果 → 用缓存，计入「复用」（任何对话页都查，不花额度）
        └─ 都没有
              ├─ 自己的帖子且自动判断开着 → 进队列：攒 2 秒或满 20 条 → 后台 → 模型
              └─ 别人的帖子 → 等用户点「判断本页回复」
                                              ↓
                                  写缓存 → 回到页面 → 显示分数标签
                                                      └─ ≥ 阈值 → 折叠
```

## 4. 各部分设计

### 4.1 推文 ID、主帖和回复间隔

- **推文 ID**：在 `shared/parse-tweet.ts` 加 `extractTweetId(article)`，从 `time` 元素外层的 `/status/` 链接取，排除引用推文。
- **回复间隔**：同样从 `time[datetime]` 取发布时间，算出回复比主帖晚多少秒，送给模型作为信号。
- **粉丝数和蓝 V**（提示词第 2 版加入）：蓝 V 看作者名区域里的 `svg[data-testid="icon-verified"]`（2026-10-20 在真实页面确认）。粉丝数先读拦截器写在作者名区域上的 `data-xf-followers-count`（`data-xf-screen-name` 要和作者对得上），再读页面脚本的内存缓存 `userMetricsMemory`；两处都不受「粉丝数」显示开关影响。拿不到时送 null。还在排队的回复，每次扫描都用最新数据替换，粉丝数晚到也能送出去。
- **主帖记忆**：按详情页的推文 ID 记住主帖的 ID、正文、作者、发布时间，以及排在主帖上方的上级推文的 ID。主帖滚出页面后，仍然用记住的正文作为上下文。
- **现有扫描器的问题**：`findMainTweetIndex` 在主帖和回复框都不在页面上时返回 0，把页面上第一条推文当成主帖。这条推文不评分；如果原来被隐藏了，会被 `applyAllow` 重新显示。改法：主帖不在页面上时，按记住的主帖和上级推文 ID 判断，其余推文都算回复。
  - 2026-10-20 在真实页面确认（内置浏览器、我的账号、一条 1062 回复的帖子）：滚到约 3300 像素后，主帖和 `inline_reply_offscreen` 都不在页面上，页面上第一条是回复。
  - 同时确认：详情页主帖的 `time` 外面没有链接，ID 靠后备规则从 `/status/` 链接取；主帖里被引用帖子的图片链接（`/他人/status/…/photo/1`）能被 `isInsideQuotedTweet` 排除。回复的 `time` 外面有 `/status/` 链接。
- **自己的帖子**：主帖作者等于 `getOwnHandle()`。
- **不送判断的回复**：主帖本身、主帖作者的回复、登录账号自己的回复、规则已经会隐藏的、没有正文的。不送的回复没有分数标签、不折叠、不计入标题栏按钮的条数。
- **「发现更多」**（2026-10-22 加）：帖子页最底下「发现更多 · 源自于整个 X」推荐的是别的帖子，不是回复。以前规则过滤和 AI 判断都把它们当回复处理（用户截图里一条推荐帖子显示了「AI 5」）。
  - 认法：拦截脚本同时把推文的对话 ID（`conversation_id_str`）写到 `data-xf-conversation` 上；扫描器记住主帖的对话 ID，对话 ID 不同的推文按主帖处理：不评分、不送 AI、已经隐藏的放出来。
  - 不用「发现更多」标题来认：标题是一个 `h2`，没有专门的标识，文字随语言变；往下滚时标题会被移出页面，后面的推荐帖子就认不出来了。
  - 拦截脚本还没写上对话 ID 时，照原来的做法当回复处理；写上后发事件重扫，已经隐藏的会放出来。如果这期间已经排进自动判断的队列，仍会送出去（推论：拦截脚本一般在扫描前就写好了，见下一条的实测）。
  - 真实页面实测（内置浏览器、我的账号，2026-10-22）：一条帖子 8 条回复的对话 ID 都和主帖相同；「发现更多」下面的推荐帖子对话 ID 是它自己的 ID。
  - 主帖作者的回复是 2026-10-22 加的。起因：作者在自己帖子下回复一条评论、讲自己的经历，被判 82 分并折叠。送给模型的上下文只有主帖，模型不知道这条回的是哪条评论，理由写的是「与原帖内容完全无关」。
- **被回复的评论**（2026-10-22 加，提示词第 3 版）：回复别人评论的回复，把那条评论（作者、正文）作为 `replyTo` 一起送给模型。同一个原因：只看主帖时，回评论的回复容易被当成「和原帖无关」。
  - 回的是哪条：X 的推文数据里有 `in_reply_to_status_id_str` 和 `in_reply_to_screen_name`，在推文元素往上第 13 层 React 组件的 props 里（2026-10-22 在真实页面确认）。这份数据只有页面脚本能读到，所以由拦截脚本（`shared/reply-target.ts`）读出来，写到推文元素的 `data-xf-reply-of`（对应的推文 ID）、`data-xf-conversation`（对话 ID）、`data-xf-reply-to`、`data-xf-reply-to-user` 上，扫描器从属性上读。
  - 拦截脚本只在对话页和 Deck 页写；每个元素、每条推文只找一次，写好后发 `xf-reply-target-updated` 事件，扫描器收到后重扫。被回复推文 ID 也算进每条回复的处理指纹，属性晚到时这条会重新处理，还在排队的回复用新内容送出。
  - 评论正文：扫描时把本页每条推文的作者和正文按 ID 记下（换页清空）。被回复的评论一般排在这条上面，已经记下了；没记下时只送作者，正文为空。
  - 直接回主帖的回复不带 `replyTo`。
  - 真实页面实测（内置浏览器、我的账号）：一条 7 条推文的帖子，被回复对象全部认对，作者回 CLEC168 的那条取到了 CLEC168 的评论正文；一条约 1200 回复的帖子往下翻 6 屏，25 条推文都读到了数据（这条帖子页面上没有回评论的回复）。每扫一遍页面上的推文用时 0.1–4.2 毫秒（已经写过的不再找）。

### 4.2 判断标准和提示词

提示词分两段：判断标准、输出格式。输出格式由插件固定追加在后面。提示词分中英两版，跟插件界面语言（和 `ai-repost.ts` 的做法一致），理由文字也用这个语言。

现在是第 4 版（`REPLY_SCORE_PROMPT_VERSION = 4`，文字自己写，思路参考 x-reply-guard）。第 3 版在第 2 版上加了第 6 条判断原则和输入里的 `replyTo`，见 4.1「被回复的评论」。第 4 版只改输出格式，判断标准没变，见下面的「输出」。每次版本号变了，旧缓存作废，回复会重新判断一次。

**为什么改第 2 版**：2026-10-20 在一条讲「飞书 → Skill → 博客 → 公众号 → X」发布流程的帖子下试第 1 版，几条「先认同、复述原帖细节、结尾补一句建议或提问」的回复只得了 10–45 分。第 1 版判断原则写了「追问原帖细节的回复更可能是真人，要减分」，模型照做了：标了「复述原帖」（强信号）却只给 15–20 分。这批回复里 6 条有 4 条用了「稳」（更稳了、稳得多、很稳、挺稳），「同批雷同」当时是弱信号，模型一条都没标。样例集的 AI 样例也全是老写法（emoji、Great point），测不出这个问题。

判断原则：

1. AI 自动回复有两种常见写法：通用夸奖（放到哪个帖子下都成立）；先认同、用原帖细节复述原帖、结尾补一个小建议或问题（看起来具体，但没有原帖以外的信息）。
2. 只按证据打分，没有信号就给低分。
3. 只有原帖里没有的信息才算真人特征、可以减分：自己的经历、自己的数字或做法、具体的反对意见、错别字和口语。复述原帖细节、顺着原帖问一个问题，不算真人特征。
4. 观点偏激、语气差、外语不地道、营销推广，都不算 AI 的证据。
5. 打分前先通读整批，比较回复之间的用词和句式。
6. 带 `replyTo` 的回复是在回那条评论：切题、复述按那条评论判断，原帖只作背景，和原帖关系弱不算证据；`replyTo` 的正文为空时，也不因为和原帖关系弱加分（第 3 版新加）。

| 编号 | 信号 | 强度 |
|---|---|---|
| S1 | 万能回复：没有接住原帖的具体内容，放到别的帖子下面也成立 | 强 |
| S2 | 复述原帖：用原帖的细节或术语换个说法重复原帖观点，没有原帖以外的信息 | 强 |
| S3 | 结构整齐：几十字的回复也有总分总、排比，句子长短一致 | 中 |
| S4 | 「不是……而是……」这类翻转句 | 中 |
| S5 | 结尾一句总结，或拔高到「本质上」 | 中 |
| S6 | 结尾提问求回复（不针对具体内容） | 中 |
| S7 | 套话：「值得注意的是」，空泛的肯定如「很稳」「很清晰」「很省心」，Great point | 中 |
| S8 | 祝福结尾，或几乎每句带 emoji | 弱 |
| S9 | 回复间隔很短，内容却很长 | 弱 |
| S10 | 同批雷同：几条回复用相同的关键词、句式，或复述同一段内容；每条都算（第 1 版是弱信号） | 中 |
| S11 | 认同 + 复述 + 补一句：开头认同，中间复述原帖要点，结尾补一个小建议或二选一的问题（第 2 版新加） | 中 |
| S12 | 蓝 V 但粉丝少于 200：只作辅助，没有其他信号时不能单靠它打到 31 以上（第 2 版新加） | 弱 |

打分规则：强信号加 30–40，中信号加 15–20，弱信号加 5–10，命中几个加几个；真人特征减分。

输入：

```json
{"parent":{"author":"…","text":"…"},"replies":[{"id":1,"author":"…","text":"…","delaySeconds":41,"followers":64,"verified":true,"replyTo":{"author":"…","text":"…"}}]}
```

`id` 是这批里的序号（从 1 开始，第 4 版起代替 19 位推文 ID）。`replyTo` 只在回复别人评论时有，正文同样截到 500 字。

输出（第 4 版）：

```json
{"results":[{"i":1,"s":82,"g":["S1"],"r":"31 分以上才写，不超过 20 字，引用回复原词"},{"i":2,"s":10,"g":[],"r":""}]}
```

- `i` 序号、`s` 分数、`g` 信号、`r` 理由。30 分以下理由给空字符串。英文版理由不超过 15 个词。
- **为什么改第 4 版**（2026-10-22）：用户反馈回复一多就容易超时。按字数估算，第 3 版一批 20 条要输出约 1000 token（每条约 105 字符：19 位推文 ID、完整字段名、40 字以内的理由），输出速度每秒 40 token 时就要 25 秒，正好是当时的超时时限。第 4 版每条 31 分以上约 52 字符，30 分以下 28 字符；按 20 条里 15 条低分推算，一批约 300 token。字数是实测，token 数是估算，没有用真实接口测耗时。请求内容 20 条从 3202 字符降到 2813 字符，系统提示词从 1660 字符变成 1688 字符。
- 解析时按请求里的顺序把序号换回推文 ID；也认旧格式（`id` `score` `signals` `reason`），`id` 先当推文 ID 认，认不出再当序号。
- 正文截到 500 字。
- `temperature` 设为 0。只对已知支持的服务（`api.openai.com`、`api.deepseek.com`）带 `response_format: json_object`；其他服务不带，从返回文字里提取 JSON。
- 解析容错：缺序号的条目丢掉；分数四舍五入并截到 0–100；不在本批里的序号或 ID 丢掉；整批解析失败按失败处理，同一条最多重试 2 次。
- 提示词带版本号 `PROMPT_VERSION`，改了提示词，旧缓存作废。

### 4.3 打分请求

- `AiRequest` 加 `XF_SCORE_REPLIES` 类型，带 `locale`。沿用现有机制：一次请求一个连接，页面关掉就取消。
- **超时**（2026-10-22 改，`shared/ai-deadline.ts`，所有 AI 请求共用）：原来每个请求固定 25 秒就中断，流式返回时还在出结果也会被切断。现在按「多久没有新数据」算：
  - 第一段数据 25 秒内要到。扩展后台收不到响应超过 30 秒可能被关掉；不流式的请求整段返回才算第一段，所以和以前一样是 25 秒。
  - 之后每收到一段数据重新计时，连续 15 秒没有新数据才中断，提示「AI 服务连续 15 秒没有返回新内容」（`error.aiStalled`）。思考片段和服务端的保活注释也算新数据。
  - 从开始算最长 90 秒。
  - 页面侧的兜底计时从 30 秒改成 95 秒。等待期间页面每 10 秒通过连接给后台发一条保活消息（`XF_AI_KEEPALIVE`），后台不处理。扩展后台 30 秒内没有任何事件可能被关掉，读模型的流式返回不算事件。
- 接口地址和 key 用 AI 转发的设置。另加「打分模型」设置，留空时用 AI 转发的模型。
- 后台另加一个只查缓存的消息 `XF_LOOKUP_REPLY_SCORES`，不调用模型。

### 4.4 缓存

- 存在后台的 IndexedDB（插件自己的数据库），不存 `storage.local`。原因：`storage.local` 每写一次，所有 X 标签页都会收到变更通知；x-reply-guard 把缓存放在 `storage.local`，每次读出整份缓存再整份写回，页面脚本还得专门过滤掉这类通知。
- 键：推文 ID。值：分数、信号、理由、模型名、提示词版本、时间。
- 保留 7 天，最多 5000 条，超出时删最旧的。
- 页面脚本另存一份在内存里，同一页面内不重复向后台查询。

### 4.5 待打分队列

新文件 `content-scripts/spam/ai-scorer.ts`。

- 去重：同一推文 ID 已在队列里或请求中，就不再加入。
- 攒批：自动模式攒 2 秒，或满 20 条就发。每次调用有固定开销，批次大一些更省额度。
- X 只渲染视口附近的推文，页面上有的回复就送，不另做视口判断。
- 同一页面同时只有 1 个请求。
- 每日上限只限自动判断，默认 300 条；手动判断不计入。
- 自动判断暂停时说明原因：没填 key、没授权接口域名、已达今日上限、已关闭、请求出错（附错误说明）。
- 切换页面时清空队列，并取消进行中的请求。

### 4.6 显示和折叠

- **分数标签**：打过分的回复，在操作栏（回复、转发、喜欢那一行）末尾显示「AI 82」。0–30 灰，31–69 黄，70–100 红。鼠标悬停显示理由和命中的信号名。
- **判断中**：已送出、还没返回的回复显示「判断中」。
- **折叠**：分数 ≥ 阈值（默认 70）的回复，隐藏原回复，在前面插一行：

  ```
  AI 82 · 万能回复、结尾提问 · @handle        展开   机器人   真人
  ```

- 点「展开」后，这条在本页内不再折叠（记在内存里）。
- **手动按钮**：放在帖子页顶部标题栏右侧，显示「AI 判断本页 N 条」，点一次送本页还没判断的回复，最多 20 条；还有剩余时按钮上的条数随之更新，再点继续。
- 结果回来时，「结果版本号」加 1 并参与扫描指纹，然后触发一次扫描。现有扫描会跳过文本没变的推文，不加这一步，结果回来后不会生效。
- X 滚动时会重建推文的元素。结果按推文 ID 存，下次扫描时重新套用。
- 调试模式：评分条里加一行 AI 分和信号，不折叠。
- 标签、折叠条、按钮的选择器加进 `XF_SELF_SELECTOR`，插件自己插入的元素不触发扫描。

### 4.7 标注

- 入口：回复操作栏里分数标签的后面，「机器人」「真人」两个图标按钮；折叠条右边也有这两个按钮。没有分数的回复（不在自动范围内、还没判断）也有。
  - 2026-10-20 实现时改了位置：原来打算放在右上角的选词、名单按钮旁边，改成和分数放在一起，标的时候能对照分数。1280 宽实测：按钮 24 像素高时把操作栏从 20 撑到 24 像素（不换行），所以改成 20 像素高，和操作栏原高度一致；改后没有再实测。按钮和折叠条在深色主题下看过，能看清。
- 已标的那个按钮高亮（机器人红色、真人绿色），再点一次就撤销。
- 存在后台 IndexedDB 同一个数据库的 `labels` 表（数据库版本升到 2，原有分数缓存保留），不过期：推文 ID、标注、作者、正文、主帖作者和正文、被回复的评论（第 3 版起，回评论时才有）、回复间隔、粉丝数、是否蓝 V、当时的分数和信号和理由、模型名（从打分缓存取）、提示词版本、时间。
- 查缓存时一起取回标注；页面上点了以后马上生效，再交给后台保存。
- 标注后的效果：
  - 标「真人」：这条不折叠（已折叠的马上显示出来）。
  - 标「机器人」：这条马上折叠，没有分数也折叠；之前点过「展开」的也重新折叠。折叠条写「已标为机器人」，拦截记录里多一个「已标机器人」。

  - 不自动改白名单、黑名单。

  - 这个功能加上之前标的：后台启动时，如果还没有这个列表，把标过「机器人」的回复的作者补进去。
  - 这个账号的回复：折叠条写「账号标过机器人 · @用户名」，机器人图标亮着；不自动送模型（不花额度），不算进标题栏按钮的条数；有缓存的分数照常显示。可以点「展开」，展开后标签后面有「收起」。拦截记录写「账号标过机器人」。

    | 这条自己标的「机器人」改成「真人」 | 显示 | 移出列表 |
    | 只因账号被折叠的这条标「真人」 | 显示 | 不变，其他回复照常折叠 |

  - 设置区「我的标注」显示「标过机器人的账号 N 个」。没有做账号列表的查看和逐个移出界面。

## 8. 用量估算

x-reply-guard 说明文档里的实测（DeepSeek flash）：每次调用固定开销约 750 输入 token，每多一条回复约加 100；5 条回复约输出 350 token，即每条约 70。

按这组数字推算（未实测）：

- 每批 20 条：输入约 750 + 20 × 100 = 2750，输出约 20 × 70 = 1400。
- 第 4 版提示词减少了输出：按 4.2 的字数，20 条里 15 条低分时一批输出约 300 token（推算）。
- 每 1000 条回复：约 14 万输入、7 万输出。费用按所用模型的单价算。
- 默认每日自动上限 300 条，约 15 次调用。

第 1 步的验证脚本和第 2 步的「用样例集测试」按钮都会记录实际用量，之后用实测数字替换这一节。跑一次样例集约 5500 输入、1750 输出 token（推算）。

## 11. 对照 x-reply-guard 的结论

| 项目 | x-reply-guard | 本方案 |
|---|---|---|
| 推文 ID、按 ID 重新挂标签、带主帖上下文、JSON 容错、7 天缓存、每日上限、失败重试 2 次、跳过自己的回复 | 有 | 一致 |
| 判断标准 | 10 个分强中弱的信号，返回信号编号 | 采纳思路，文字自己写（4.2） |
| 分数 | 一个 AI 嫌疑分 | 采纳，放弃三项分 |
| 自动判断范围 | 只在自己帖子下；别人帖子手动；其他页面只查缓存 | 采纳（4.5、4.6） |
| 回复间隔 | 送给模型 | 采纳（4.1） |
| 主帖滚出页面 | 记住主帖信息 | 采纳，并修正现有扫描器（4.1） |
| 提示词验证 | 真实接口跑带预期的样例 | 采纳（4.8） |
| 暂停原因 | 按钮上显示 | 采纳（4.5） |
| 折叠、规则先筛、标注 | 没有 | 保留 |
| 缓存存储 | `storage.local` 整份读写，没有条数上限 | 用后台 IndexedDB，有上限 |
