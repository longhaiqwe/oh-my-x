# 粉丝与关注分析：融合设计

日期：2026-11-11。版本：第二版，已逐张查看原文11张图片后修订。状态：设计提案，尚未接入扩展。

## 结论与依据

可以加入。第一期聚焦粉丝构成、分档名单与 CSV 导出；随后增加关注分析。现有六个一级模块保持不变，在「数据 → 看板」新增「粉丝与关注分析」，主要使用入口放在 X 的关注者／正在关注列表。账号状态、通知提示和内容复盘分别扩展原有功能，避免另建重复入口。

本设计依据用户提供的文章、文中11张图片及当前工作区代码，包含工作区中已有的未提交修改。第一版只读取正文，未核对图片；第二版修正了这一遗漏。未下载、运行或审计文章所述插件；不保证其字段在当前 X 页面全部存在。原型使用合成数据，不代表任何真实账号，也不是扩展功能的运行结果。

技术栈：WXT、Vue 3、Tailwind 4、reka-ui。设置界面已有语义变量与明暗主题；X 注入界面使用原生 DOM、`getThemeColors()`、`ACCENT` 和 X 字体。延续两套现有规范，不引入框架或主题依赖。

## 能力取舍与归属

| 文章能力 | 现有基础 | 融合位置与阶段 |
| --- | --- | --- |
| 粉丝构成、分档名单、导出 | 用户指标拦截、UserCell 粉丝徽章 | 第一期：「数据 → 看板 → 粉丝与关注分析」；关注者列表的统计条打开详情 |
| 关注列表筛选、排序 | 「互动」的未回关标记 | 第二期：正在关注列表复用分析面板；原有标记开关保留，增加通往分析设置的文字入口，只有一份配置 |
| 账号状态 | 粉丝数徽章目前只提供原生 title 提示 | 第三期：徽章支持点击／键盘打开详情，悬停也可打开；事实字段缺失写「未获取」，不等同于安全 |
| 新关注者提示 | 通知用户卡片已整理关注、点赞、回复等事件 | 第三期：仅在明确的关注事件中补粉丝数与阈值标签；不新增通知页，不把点赞误标为关注 |
| 推文复盘 | 博主活动度、爆款雷达、比例徽章 | 后续扩展「博主活动度」的内容表现；展示样本时段表现，不断言「最佳发帖时间」 |
| 评论区高粉丝账号标记 | 已有作者粉丝徽章与垃圾过滤 | 后续作为现有粉丝徽章的可选强调；不默认加金线或因粉丝少而淡化回复 |
| 分享名片 | 未发现直接对应功能 | 暂缓；将来从分析结果的导出菜单进入，导出图片必须带样本范围与采集时间 |
| 质量总分、疑似互粉判定 | 缺少验证过的质量模型 | 不纳入。粉丝数、注册时间、关注比不能单独证明可信度或互粉行为 |

不复制原文「万粉账号关注等于业内认可」「新号或小号说明低质量」的判断。功能提供可核对的公开数字和名单，不输出账号质量评级。

## 入口与页面结构

### X 页面

在明确的 `/{handle}/followers`、`/{handle}/verified_followers` 和 `/{handle}/following` 列表上下文中提供统计条，放在原生标签栏之后、用户列表之前，不占用个人主页昵称旁已有的收藏／加列表位置。认证粉丝使用独立样本与标题；共同关注、推荐账号不进入名单。2026-11-12 按用户要求补充认证名单支持。

统计条默认两行：

```
已记录 264 位 / 总粉丝 18,600        [查看粉丝构成]
仅含本次浏览已加载的名单 · 数字资料可用 264 位
```

第一行说明对象与范围；按钮为此区域唯一主要操作。分母不可用时写「总粉丝未获取」。开启前显示「开启粉丝分析」与本地记录说明，用户点击后才开始本功能采集。整个功能默认关闭，不影响现有粉丝徽章。

点击打开最大宽度1040px的模态分析窗口，四周留24px，带遮罩，背景不可交互；不改变原生列表宽度或滚动位置。≤700px改为全屏；关闭或点击「返回列表继续加载」后恢复原列表与焦点。分析与继续加载是两个明确步骤，避免分析时样本持续变化、名单排序跳动。

窗口固定当前列表的账号与类型，标题必须写出目标账号。离开目标路由、切换列表类型或登录账号时关闭窗口并取消待写入批次；不静默更换分析对象。设置中的历史记录详情复用同一分析内容。与回看等面板互斥，保存并恢复各自状态。

### 宽窗口的内容结构

1. **标题**：粉丝构成、目标账号、关闭按钮。范围行紧接标题，写「已记录264／总粉丝18,600」「264位有粉丝数资料」。
2. **三个累计阈值**：≥3千96位（36.4%）、≥1万44位（16.7%）、≥3万18位（6.8%）。沿用原图信息，数字从演示数据计算；三个条件有包含关系，明确写「人数不能相加」。点击任何指标可筛选名单。
3. **左侧320px：六档分布**。互斥分档、水平条形图、人数、比例。按同一线性尺度绘制；保留准确数字，不因小值难看而放大条形。选中行用勾选和浅底色表示，不只依赖颜色。
4. **右侧：具体账号**。结果数、选中条件、搜索与排序，之后是两列紧凑账号项。每项展示名字、用户名、精确粉丝数；每页12位，点击分档时在原位更新名单。头像使用中性占位进行演示。原型不提供虚构账号的外部跳转。
5. **固定底部**：采集时间、仅本机说明、导出CSV、返回列表继续加载。导出为次要操作，包含筛选后的全部结果。清除记录移到设置，避免在分析主界面与正常操作并列。

与第一版的差别：不再把“首屏仅保留一个数字”作为硬性选择。三个阈值回答不同的问题，可以保留在同一组内，用相同字号和中性底色控制权重；它们不是三个独立主操作。左侧分布和右侧名单同时可见，避免先滚过整个分布区才看到具体账号。

### 窄屏不是桌面的纵向堆叠

≤700px使用「分布概览／账号名单」两个视图，保留同一筛选状态：

- 概览：范围、三个汇总指标、六档分布，底部「查看符合条件的N位账号」。点击分档仅改变选择，点击按钮进入名单，避免点击即跳走导致难以比较其他档位。
- 名单：结果数与筛选条件、搜索、排序、单列账号项。可切回概览修改分档，搜索和排序保留。
- 标题与底部操作固定，中间独立滚动；空状态隐藏无效标签和工具。
- 关注分析在窄屏变为账号卡片，每项分两层显示身份／关系与粉丝数／关注数／比例，不压缩成横向滚动表格。

默认分档是 `[0,3000)`、`[3000,10000)`、`[10000,30000)`、`[30000,50000)`、`[50000,100000)`、`[100000,+∞)`，界面显示「不足3千」「3千–不足1万」等，不重叠。它与当前粉丝徽章的五档配色含义不同，因此用中性柱形，不复用五档评级颜色。后续详细设置允许五个严格递增的非负整数阈值；改变后从原始数据重算，不重采集。首期固定分档以降低配置负担。

### 设置界面

「数据 → 看板」保持原创内容奖励计划、博主活动度现有顺序，其后加入一张 `FeatureCard`：

- 名称：粉丝与关注分析。
- 说明：整理已加载的名单，查看粉丝数分布与具体账号。
- 主开关：记录已加载名单，首次安装和升级默认关闭。
- 在哪用：X 的关注者和正在关注列表。
- 状态：已保存 N 份名单 · 仅本机；暂停后继续显示已有记录。
- 次要操作：查看已存名单、详细设置。

详细设置使用既有 `SubPage`。首期包括开关、保存上限说明、按目标账号／列表类型列出的本地记录、清除单份与清除当前登录账号全部记录。删除需确认；暂停采集不删除。关闭功能后 X 内入口移除，已有数据仍可从设置的只读详情查看与导出；无 X 标签页也能看本地记录。打开 X 原始列表属于独立次要操作。

完整设置页与 popup 共用组件，不在设置页自动扫描后台账号。原型的设置页只展示位置与开关层级，不实现存储管理。

## 数据边界与可行性

### 已经具备的基础

- `shared/user-metrics-interceptor.ts` 能从 GraphQL／部分 REST 数据提取用户名、昵称、粉丝数、关注数和用户 ID。
- `entrypoints/interceptor.content.ts` 已拦截 fetch／XHR，广播资料；也可从页面 React 数据补充徽章资料。
- `content-scripts/features/user-followers.ts` 已定位 UserCell、过滤 socialContext 中的其他账号、展示粉丝数。
- `colors.ts`、`xTypography.ts`、回看面板可提供注入页面的主题、排版和面板组织参考。

### 必须补充，不能从现有缓存推算

现有 `extractUserMetrics()` 会递归收集同一响应里的所有用户，并同时以 handle 和 ID 作索引。它没有「这些用户属于哪一个账号的哪一类名单」的信息。直接统计缓存会把推荐账号、转推作者等混入，而且同一人可能计数两次。

新增独立的名单解析器：请求发起时记录目标 user ID、列表操作类型、登录账号上下文与路由代次；只接收明确属于该列表的用户条目，排除推荐模块。以 user ID 去重，并从资料缓存补字段；不能反向把缓存中所有账号加入名单。DOM／React 补充仅针对已验证的列表行。上下文不明确时不入库，迟到响应不能写入新账号。

建议分层：

```
X 原生列表响应（只读）
 → 名单上下文＋条目解析（新增）
 → 校验后的名单增量（MAIN → isolated）
 → 后台统一写扩展 IndexedDB
 → 纯函数统计／筛选／CSV
 → X 统计条与宽窗口；设置中的本地只读详情
```

候选新增文件：`shared/audience-types.ts`、`audience-parser.ts`、`audience-summary.ts`、`audience-store.ts`、`audience-export.ts`，以及 `content-scripts/features/audience-insights.ts` 和 `AudienceInsightsCard.vue`。接入既有初始化、开关变更、后台 RPC、功能注册表和中英文文案机制。只在明确列表响应上执行名单解析，避免对每条推文做额外全树扫描。

目前两端用户缓存主要用「粉丝数是否变化」判断更新。如果未来追加关注关系或账号状态，粉丝数不变而其他字段变化时会被忽略。应增加独立的资料合并机制：区分缺失值与明确的 false／0，按字段和观察时间更新，避免扩展现有缓存后产生陈旧数据。

### 统计口径

- N：当前采集批次中，已确认属于此名单的去重账号数。
- K：其中拥有有效粉丝数的账号数；分档比例的分母是 K，未知值不归入最低档。
- M：目标账号最近观察到的总粉丝数／总关注数，同时保存时间和是否为近似显示值；不可获得精确值时不计算精确覆盖比例。
- N/M 仅称「已记录占比」，不是随机抽样覆盖率；X 返回顺序可能有偏，不提供置信区间或总体外推。
- 即使滚动到底或 N≈M，也不自动宣称「完整粉丝名单」；不可见账号、接口限制及时间差都可能影响结果。
- 注册时间、关系状态、认证或限制标记等都须单独记录字段可用率。未获取不等于没有。
- 新账号筛选若后续加入，以确切注册时间为准；粉丝不足100和不活跃没有等价关系。

### 持久化与请求

第一期为该功能设定「不新增 X 接口请求、不自动滚动」的边界。不能把它写成整个 oh-my-x 的承诺：项目已有帖子同步、活动度扫描、Lists 等主动请求。现有粉丝徽章的读数逻辑仍按现状运行。

建议初期上限：每个登录账号最多 3 个目标账号；每个目标的粉丝名单最多 20,000 条、关注名单最多 10,000 条；本功能全库硬上限 100,000 条或 30 MiB（估算序列化负载），先到者停止追加。上述为设计预算，尚未做空间和性能实测；实际 IndexedDB 占用可能更高，必须处理配额异常。

每个名单保存一个有起止时间的采集批次。短时间内继续滚动可续入当前批次；间隔超过24小时再访问时，保留上次记录为只读，提示「开始新记录」或查看旧记录，不自动跨天合并。开始新记录会明确替换同一目标、同一列表的旧批次。旧记录缺少某人不能解释成取关，也不提供“新增粉丝日报”。达到目标数／条数／容量上限时停止追加并提示管理空间，不静默删掉另一份记录；已有条目仍允许补全资料。

按登录账号 ID、目标账号 ID、列表类型、采集批次隔离。登录身份无法可靠识别时只保留当前页临时记录，明确提示不会持久保存；账号切换立即隔离。禁止把列表成员存入 x.com 的 localStorage／sessionStorage，持久化放扩展源 IndexedDB。保存必要字段和时间，不保存原始响应、Cookie 或私信。

CSV 包含目标、列表类型、采集批次、用户 ID、用户名、名字、粉丝数、关注数、观察时间、字段缺失情况；后续关系字段单独注明它相对哪个登录账号。导出当前筛选的全部结果，正确处理 BOM、换行、引号以及 `= + - @` 等公式起始字符。

## 关注分析的补充规则

复用窗口、样本范围和导出机制，关注分析采用独立的筛选／表格布局。「未回关」只在确认目标就是当前登录账号、且关系资料明确时可选；第三方的关注列表仅提供规模分布，不把「对我关注关系」误当成「对列表主人关注关系」。筛选逻辑使用明确 true／false／unknown 三态，未知不纳入未回关结果。界面文案用「未关注我」，比「未回关」更准确：它只描述当前关系，不推断过去是否回关。

桌面第一行为关系筛选「全部90／未关注我50／已关注我34／关系未获取6」；第二行为属性筛选「≥1万粉丝／注册未满90天／不足100粉丝」。关系单选，属性可以叠加，彼此取交集。属性上的人数表示当前关系组内单独满足该条件的数量，不随其他属性条件交叉重算。表格展示账号、粉丝、关注、粉丝/关注比、与我的关系，数值右对齐，缺失值写未获取，关注数为0时比例显示“—”。搜索和排序在名单标题旁，不放到设置中。

保留原生关注按钮，不提供批量取关；分析列表提供「查看主页」或回到 X 原始列表。粉丝关注比仅在关注数有效且大于0时计算，否则显示「—」。粉丝量、关系筛选和搜索取交集，排序缺失值固定放末尾。

## Refactoring UI 约束与状态

设计顺序：先以灰阶确定范围提示、累计阈值、分布与名单的层级，再仅给可点击／选中态加入 X 强调色。原型提供灰阶开关便于审阅。

| 原则 | 具体落实 |
| --- | --- |
| §2.1 信息层级 | 范围在数字之前；三个累计阈值属于一个信息组，分布与名单同屏，名单承担核对任务 |
| §2.4 降低次要元素权重 | 导出用次要描边按钮，窄屏改为中性浅底；不做六个彩色统计卡，不给每行加阴影 |
| §2.8 操作层级 | 原始列表主操作为查看分析；分析中筛选后核对名单，底部主操作是返回原列表继续加载，导出次要；窄屏概览的主要操作为进入筛选后的名单 |
| §3.6 分组间距 | 区块间24px、区块内12px、名称与说明4px；宽窗口内边距24px，窄屏16px |
| §4.7 数字对齐 | 人数和比例右对齐，数字等宽；长名字省略但完整用户名仍可查 |
| §5.7 不只靠颜色 | 选中项增加勾选标志及文字；状态用文字解释 |
| §8.4 空状态 | 首次无数据时隐藏图表、无效搜索和导出；给出继续浏览的唯一主操作 |
| 项目规范优先 | 设置字号12/14/16/18/20、字重400/600、现有米白／深蓝语义色；X 内沿用 X 主题，不复制设置页橙色 |

| 状态 | 展示与动作 |
| --- | --- |
| 未开启 | 开启后仅记录本次及之后加载的名单；不开启不建库 |
| 已开启但无记录 | 「还没有可分析的名单」，提示关闭面板并在原始列表向下浏览 |
| 有名单但 K=0 | 显示 N 与「粉丝数资料未获取」，隐藏分布和百分比，可查看账号名单 |
| 部分字段缺失 | 显示 K/N，保留未知项；可单独筛选「粉丝数未获取」 |
| 小样本 | 标注样本数，不给最低样本量达到就自动可靠的承诺 |
| 无筛选结果 | 保留图表和工具栏，提示更改筛选，提供「清除筛选」 |
| 解析失败 | 「暂时无法识别此列表」，保留 X 原列表；不把错误展示成0位粉丝 |
| 到达上限／配额不足 | 保留已有记录并暂停追加；提示导出或清理后再继续 |
| 旧记录 | 显示起止时间与「历史记录」，不自动混入本次浏览 |
| 路由／登录账号改变 | 关闭面板、取消待写入并隔离数据；返回可恢复 |

桌面与窄屏均采用模态语义和焦点循环，背景 inert；Esc关闭并返回入口，恢复原始列表位置。原型顶部的设计评审工具不属于产品界面，可用于切换场景；实际产品不包含这些工具。触控目标44px；图表行可按 Tab、Enter／空格筛选。数字更新使用节流后的礼貌播报，不抢焦点。主题包含亮色、暗色、深蓝；原型检验明暗与灰阶，真实 X 强调色组合待接入时验证。

## 实施顺序与验收条件

1. 先采集真实 X 返回夹具，核对普通粉丝／关注列表、路由身份与条目来源；确认缺失字段与特殊列表边界。未验证前不承诺账号状态字段可用。
2. 第一阶段交付粉丝构成、分档名单、搜索排序、CSV、本地记录与清理。验证重复条目、未知粉丝数、迟到响应、账号切换、跨天批次与容量上限。
3. 第二阶段加入关注分析，先验证 followed-by 语义与登录账号绑定，再开放未回关筛选。
4. 后续独立设计账号事实详情、通知阈值提示、内容复盘。原图明确仅使用发出一天以上的帖子比较时段，必须保留这一约束，并展示每个时段的样本数；同时继续控制帖子年龄和浏览累计时间。仅筛掉不足一天的帖子仍不能消除所有观察时间差，不据此断言最佳发帖时间。

正式实现的验收目标：手工夹具分档人数／比例与导出结果一致；只开关、浏览、分析该功能时新增 X 接口请求为0；过滤命中可导出超过100行；≤700px 无横向溢出；键盘可完成打开、筛选、导出、关闭；失败不影响 X 列表。性能预算待真实样本验证，不声称已达成。

## 本轮发现的文档与代码差异

1. README「未回关」描述为在自己的正在关注列表生效；`changeHighlightNonFollowers()` 实际只检查路径含 `/following`，没有校验列表主人是否为当前登录账号，并按「没有 userFollowIndicator」标记自己已关注的人。新分析必须单独校验目标身份，不能把这个旧判断直接当作关系证据。本轮不修改旧功能。
2. README「博主活动度」写「在博主主页点扫描近7天」，实际扫描入口在插件的「数据」弹窗 `ProfileActivityCard.vue` 中，要求当前标签页为博主主页；未发现注入主页的扫描按钮。本设计按实际的弹窗卡片扩展，文档建议补充入口位置。
